## Activation-time specialization (18:10)

- Decision: Specialization happens when a term enters executable position and is activated by an executable-position protocol, not through a user-visible `{specialize}` function/opcode.
- Decision: Any value may be placed in executable position; malformed or non-executable normalized syntax fails at activation.
- Decision: The specialization context is supplied by the executable position (e.g. `do! fn: [x] do ... end` body context), not by ambient dynamic name lookup.
- Decision: Forged/loaded/parsed/runtime-constructed terms remain porous data until activated; activation can specialize them later.
- Decision: Vetochka has no language-level quote rule; specs must describe explicit syntax-data/activation protocols instead of quoting.
- Open: Exact executable-position protocols, especially `do!`, remain to be specified.

## L4 backbone facilities (18:45)

- Decision: Keep `load_file` and `parse_term` as v0 backbone facilities for programmer-defined module/code graph systems.
- Decision: `load_file :: path-bytes -> bytes | diagnostic` is the only required host effect in v0; module roots, imports, dependency resolution, caching, and path policy stay above v0.
- Decision: `parse_term :: source-bytes -> normalized syntax term | diagnostic` is pure and returns ordinary term data with no executable meaning.
- Decision: v0 has no `specialize`, `execute`, or `eval` intrinsic; execution is term entering executable position, which invokes L3 activation-time specialization and then L5 execution.
- Rationale: Lowest useful substrate for reusable code is host bytes plus parser-to-term. Programmers can then define module systems and vf languages using v0 protocols.
