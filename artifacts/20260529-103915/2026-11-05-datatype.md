# Synthetic datatype library exercise

Status: exploratory design, not an implemented library or an approved interface.

## Question and basis

- Request (user): assess a Datatype99-like library synthetically from `docs/new_spec/`.
- Direction (user): support library-defined languages with one generic syntax as an 80/20 solution, rather than requiring a different grammar for each DSL.
- Basis (agent): `docs/new_spec/02_syntax.md` supplies the grammar and lowering rules. The current part of `03_v0.md` supplies the interpreter/compiler model and bootstrap entry point. Its historical evaluation section is not a current implementation contract.
- Boundary (agent): the examples below use existing vf syntax. Names such as `datatype`, `match`, `fn`, and `ptr` receive proposed library meanings. The spec does not supply those libraries.

## A program written by the library user

```vf
datatype(Tree) do
    Leaf[value: i64]
    Node[left: ptr(Tree), value: i64, right: ptr(Tree)]
end

fn(sum) params:[tree: ptr(Tree)] returns:i64 do
    match(tree) do
        Leaf[value: x] do
            return(x)
        end
        Node[left: lhs, value: x, right: rhs] do
            return(sum(lhs) + x + sum(rhs))
        end
    end
end
```

Interpretation (agent, proposed): `datatype` defines a tagged union and constructors. Each list entry declares one named field. `ptr(Tree)` describes a target C pointer type. `match` inspects a pointer to a valid value of that datatype, binds its selected fields, and enters one arm. `fn` and `return` belong to the surrounding C-oriented language. Library availability is assumed here; import syntax is outside this exercise.

Finding (agent): the example requires no new parser production. Applications, application to lists, labels, blocks, and infix expressions already cover it. In particular, `datatype(Tree) do ... end` is an application to a block. `Leaf[...] do ... end` is an application to a block whose callee is an application to a list.

Limit (agent): the common grammar determines the grouping. A DSL cannot independently change those parse rules. Operator precedence is explicitly left to the interpreter. This example can choose left association for its addition chain.

## What the datatype library receives

The following uses the spec's lowering notation. `<term>` means the recursively lowered source term. `<meta>` stands for the source metadata at each occurrence, not one shared metadata value.

```vf
@[[native-string<:app-block>, <meta>]] ~[
    @[[native-string<:app>, <meta>]] ~[<datatype>, <Tree>],
    @[[native-string<:block>, <meta>]] [
        @[[native-string<:app-list>, <meta>]] ~[
            <Leaf>,
            [<value: i64>]
        ],
        @[[native-string<:app-list>, <meta>]] ~[
            <Node>,
            [<left: ptr(Tree)>, <value: i64>, <right: ptr(Tree)>]
        ]
    ]
]
```

Finding (agent): `:app-block`, `:app-list`, and `:label` expose the structure needed to recognize this declaration. Identifier spelling supplies the proposed DSL vocabulary. Tags also retain source metadata for diagnostics.

## Work performed by the library

Proposed algorithm (agent):

1. Recognize the declaration shape and read its type name.
2. Read each variant name and its labeled fields.
3. Reject duplicate variant names and duplicate field names within a variant. Retain source locations for errors.
4. Resolve field types in the target language, including the self-reference in `ptr(Tree)`.
5. Construct a forward declaration, a discriminant enum, a struct containing a union, and constructor functions.
6. Publish the variant and field information for the matching library.

This is ordinary computation over terms. A syntax library can use untagging, list traversal, and triage to implement the structural readers. Native strings and integers can support names, counters, and other working data. Their complete bootstrap API remains unspecified.

A candidate library boundary can be written with the existing closure and binding syntax:

```vf
\[decode-datatype, check-datatype, lower-datatype] do
    \[form] do
        =[declaration: decode-datatype(form)] do
            check-datatype(declaration)
            lower-datatype(declaration)
        end
    end
end
```

Boundary (agent): these three arguments are proposed library functions, not existing builtins. This sketch shows the separation of recognition, validation, and construction. It does not supply their implementations or settle the pending v0 application and binding contracts.

One candidate output fragment, still written in vf, is:

```vf
enum(Tree_tag) do
    Tree_Leaf
    Tree_Node
end

struct(Tree) do
    tag: Tree_tag
    data: (union do
        Leaf: (struct do
            value: i64
        end)
        Node: (struct do
            left: ptr(Tree)
            value: i64
            right: ptr(Tree)
        end)
    end)
end
```

Boundary (agent): `enum`, `struct`, and `union` are proposed backend vocabulary. Their appearance here is a readable presentation of constructed output terms.

## Matching and library composition

Proposed behavior (agent): the matching library resolves the subject type, checks the arms against the published datatype information, and lowers the match to C. It checks unknown variants, missing or duplicate arms, and field labels. It introduces arm-local bindings. The C emitter evaluates the subject once and selects a union member only after checking its discriminant.

Finding (agent): shared syntax makes the two libraries readable by the same parser. Semantic composition still requires a shared datatype description and a name-resolution contract. A third library, such as a serializer generator, could consume that description. The universal tree representation does not define this contract by itself.

## A concrete C target

`2026-11-05-datatype-example.c` contains a hand-derived C99 translation of the datatype and `sum`, plus a small self-check. It is an executable design example, not compiler output. The emitter's proposed names use `_make` for constructors to distinguish them from enum constants in C's ordinary identifier namespace.

The target includes a discriminant enum, a struct/union representation, two constructors, and a switch-based match. Fields store ordinary C values and pointers. The example does not infer ownership, allocate nodes, or add runtime reflection. It assumes valid live tree pointers, initialized discriminants, and sums representable by `int64_t`.

Validation results are recorded in `2026-11-05.md`. Compilation of the C example cannot validate a Vetochka parser, evaluator, generator, or performance claim.
