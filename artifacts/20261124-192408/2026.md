## Why the project exists (README, 02.04.26)

Source: `sources/cc34eed/README.md`.

Vetochka is described as "based on tree-calculus, particularly on triage-calculus". The project exists for three reasons:
1. to learn programming-language design "from a functional purist standpoint";
2. to develop "a practical, system level language with pure core";
3. "I'm one of those people who wants to develop their own lisp".

The same README summarizes the phases: reading the papers and the book (winter 2024); a first design with grammar,
internal representation and unchanged triage reduction rules (winter 2024 – spring 2025); a redesign with opcodes,
intrinsics and syntax because effects should not be encoded as pure tree terms (winter 2025); and the 17.02.26
conclusion to study the calculus itself and use its expressiveness.

## Details not in the devlog

- Byte-string literals (12.02.26, `PROJECT.md`): the lexical form was `s{...}` or `s{{{...}}}`, with the `s` inseparable
  from the braces so bare braces remained available. Compile-time functions such as `cstr`, `trim`, `detend`, `bytes`,
  `hex` and `fmt` would derive other forms. The author's note: "this is quirky and I like it". The devlog records the
  string decision at (12.02.26, 1); the prefix was later dropped (task 20260216-100019).
- Grammar (29.05.26 – 10.06.26, `sources/27fc844/docs/grammar.md`, `sources/1f3aa1d/docs/grammar.md`):
  the grammar is "also a canonical bytecode representation in utf-8 text". Mixed infix is a parse error
  (`x + y * z` must be written `x + (y * z)`). Integer literals are always i64. The first rewrite rules lower every
  postfix, label, block and operator form to `($ ...)` applications over tagged lists such as `[:block, ...]`,
  `[:label, name, expr]` and `[:infix, op]`; tags became byte strings (`{:block}`) on 10.06.26.
- Callable protocol (13.06.26, `sources/6b0bfc5/PROJECT.md`): a generic callable is a stem `^ [opcode_payload]`,
  so it applies to exactly one argument. The VM protocol is `^ [{:call}, {opcode}, [cur_arity, max_arity], [curried_args]]`.
  Every application is a binary `{$}` cell. The devlog has the stem shape and the implementation order (17.06.26);
  the arity fields are recorded only here.
- Language-family example (30.05.26, `sources/4de0cb8/project/vetochka_uniform.tree`): the first full vf-style program,
  with `def type:`, `def struct:`, `var:` and `case {click} ~do ...` arms over string-tagged variants.
- Tag guarantees (21.10.26, `sources/39f7116/docs/new_spec/02_syntax.md`): tagging does not change application
  behaviour, `(@[m] v)(x) => v(x)`. `untag` is unchecked and gives unspecified results on inputs that are not tagged
  values. A well-formed tagged value always has a tag; "no tag" is an empty proper list.
