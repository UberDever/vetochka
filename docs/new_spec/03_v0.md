# Vetochka 0

Syntax of Vetochka 0 (`v0`) is described in Section 2, but please note that vast majority of syntax is
not executable and only considered as data. Executable syntax forms are described below.

## Vetochka 0 Runtime

Runtime consists of two integrated parts: triage calculus and VM opcodes. Any node can enter an executable position, although
not any node has a sane interpretation behaviour. Further sections describe execution semantics using simple prose, on
actual execution rules please refer to [CESK evaluation rules](#v0-cesk).

### Triage calculus

`Triage calculus` is an alternative `tree calculus` model, where `rule 2` differs in resulting argument positions and
`rule 3` consists of several rules that allow for straight and efficient node matching.

Nodes in tree/triage calculi are not named, since semantically they are fully
atomic building blocks, nothing more. We've tried to use different namings like `delta`, `tree`,
and such, but `nyad` is goofy enough to remember and be distinct from the rest of the language.

Terms are built from:

- `~[]` -- the single primitive value, a nyad with no children;
- `~[x]` and `~[x, y]` -- two constructors that participate in actual rules 1-3
- binary application.

Reduction rules (incorporated as proper CESK rules later, see TODO: ):

```text
0a. ~[](x)                       -> ~[x]
0b. ~[x](y)                      -> ~[x, y]
1.  ~[~[], x](y)                 -> x
2.  ~[~[x], y](z)                -> (x(z))(y(z))
3a. ~[~[w, x], y](~[])           -> w
3b. ~[~[w, x], y](~[u])          -> x u
3c. ~[~[w, x], y](~[u, v])       -> y u v
```

This calculus has no literals, names, cells, opcodes, machine state, effects,
environments, modules, or execution policy beyond its reduction relation.

### Opcodes

Opcodes represent machine-native operations. They extend usual `triage` reduction rules
to support richer and more performant semantics: abstractions, numeric and string operations, common structures facilities and more. They are also used to do host-related actions, such as: IO, library/plugins, randomness, OS process and more.

Opcodes are selected by `$` quasiidentifier. Following notation uses `<stuff>` as a template for arbitrary node, the
type of which, hopefully, could be inferred from the context.

General opcode shape is as follows:

```
$[{namespace}, {opcode}] <param1> <param2> ... <paramN>

```

or, for core opcodes, the following notation is acceptable:

```
$<labeled-opcode> <param2> ... <paramN>
```

, where:

- `<paramN>` node adheres to rewrite rules 6 and 7, see [rewrite rules](#rewrite-rules).
- `<labeled-opcode>` label determines the opcode being selected with an immediate argument provided.

Every opcode determines if it wants to evaluate a param and how it wants to do that. Which means that all
opcodes accept raw syntax as described by rewrite rules and evaluation strategy for every application case is different.

Note that opcode shape described above is really just a continuous application, as allowed by syntax rules.
This means that every opcode is basically curried out of the box and each argument can be supplied later.
This imposes several common opcode states:

```text
Continue(next-state, inputs)
Dispatch(result)
hard trap
```

Exact state transition and dispatch action are determined by a specific opcode separately.

### Core opcodes

1. **Lambda abstraction**

Syntax:

```
$fn: [<param-identifier1>, ... <param-identifierN>] <do-end-node> to: <expr1> ... to: <exprN>
```

Semantics:

1. On `fn: [...]` opcode becomes a function with arity N; Every node in the bound list is expected to be
an identifier adhering to rewrite rule 1.
2. On `do ... end` node opcode just changes its state. This node should adhere rewrite rule 7.
3. In this state opcode could be considered a classical closure ready to be executed with supplied arguments.
4. On every consequtive `to: <expr>` node its `expr` is evaluated to receive a value under
the outer (if installed previously by the outer term) environment `E-caller`. Then, an opcode closure gets an internal binding `param-identifierN -> to-arg-valueN` to `E-fn`. No body traversal and substitution is performed.
5. When opcode is saturated, i.e. number of args matches number of params, 
`do ... end` body is entered. `E-fn` is installed, extending `E-caller` and performing shadowing for same identifiers.
Every entry in `do ... end` is evaluated in statement fashion, performing side-effects. Last expression is
returned as a term with bound `E-fn` to employ on-demand identifier resolution by outer code.

If parameter list is empty, function would be executed immediately on receiving its body.

It is a hard error to have duplicates in the list.



Example:

```
$fn: [x] do
    $fn: [y] do x end
end to: 42 to: 69
;; -> 42
```

```
$fn: [] do {stuff} end
;; -> {stuff}
```
