# The core: v0

`Vetochka` is a layered language: you have an executable core and everything else that is built around it.
This section describes this core called `v0`.

Whole `v0` and, by extension, `vetochka` built from the primitives: `leaf`, `fork` and `fruit`. The latter one is just a *plain good old-fashioned blob of bytes*.
There is nothing more than that, everything else is encoding conventions.

## Syntax

The complete syntax is located in `vf:TODO:` section. Following
syntax examples should give a clear picture for the core subset.
We introduce it as the notation to describe further subsections.

```
~                       ;; a leaf, a nil, a unit, the one and only
~[x, y]                 ;; a fork, a pair, a cons cell
~{aBCd e fg}            ;; a fruit, a blob, bytes, a payload, encoded using hex notation with whitespace
{Hello Larpers💯!}     ;; a second form of fruit, utf-8 payload inline
```

Proper lists are fundamental enough to have their own shorthand:

```vf
[]     == ~
[x]    == ~[x, ~]
[x, y] == ~[x, ~[y, ~]]
...
```

## Tagging

Every distinct non-primitive value in the language is tagged and every such value is a
tree. A tag is a list at the start of a value (a head), with a specific structure.

Rich syntax of `vetochka` is lowered to tagged trees and lowering rules are decribed in
`vf:TODO:` section.
All these rules use a tagging format defined below. We use informal placeholder-driven
notation that should be clear by its usage context.

```
tag = [<kind>, <source-id>, <byte-offset>, <byte-len>, <k-v-meta>*]
kind =
    | {$}
    | {:closure}
    | {:binder}
    | {:triage}
    | {:intrinsic}
    ...

source-id =
    | ~
    | a-string
    | a-buffer
    | a-port

byte-offset = a-i64
byte-len = a-i64
k-v-meta = [{:kv}, a-string, a-value]
```

When `byte-len` is 0, a value should be considered runtime-built or synthetic.

Specific `a-*` value kinds and their structure are described in the
`std:TODO:` section.

## Execution

The actual language execution is performed when the interpreter encounters
certain values. We call these control values.

They include:

- Application
- Closure
- Binder
- Triage
- Intrinsic

An application of one of the control value to other value usually directs computation
and usually does a particular effect, based on the kind of control value.

These values encode a specific flavour of lambda calculus named *A-Normal Form* (TODO:citation needed). It is an unusual language which doesn't have
a specified evaluation strategy, that is, you encode your own, since only
control value that forces the evaluatation is a binder.

This calculus has three kinds of expressions: atomic, complex and general.
We use the notation similar to one used in tagging section to describe such calculus.
We also use ellipsis to represent uninteresting repeated terms.

```
aexp =  [[{:closure}, ...], ???]
        | [[{:id}, ...], ???]
        | a-*                       ;; general value

cexp = [[{$}, ...], ]
```

To specify the actual execution, we use familiar CESK notation. We promise to use less math
and more common datastructures.

```text
Control, Environment, Store, Kontinuation
--- : Effect
Control', Environment', Store', Kontinuation'
```
