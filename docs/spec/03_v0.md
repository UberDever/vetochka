# Vetochka v0 Layers

Status: draft spec, recomposed 2026-07-11.

Existing project notes, memory entries, and drafts are design hints. This document
records the current v0 specification as decisions are re-formed. Conversation
ledgers preserve rationale and rejected alternatives.

## L0 Triage calculus

### Spec

Layer 0 is the pure triage-calculus core.

Terms are built from:

- `^` — the single primitive value;
- binary application.

This section writes application as `$` only inside reduction rules, to make the
applied argument visually explicit. This is not surface syntax. Surface notation
may use ordinary call syntax such as `f(x)`; implementation notation may use some
other representation. The semantic relation remains binary application of one term
to one term.

The three observable shapes are:

```text
leaf: ^
stem: ^ x
fork: ^ x y
```

Reduction rules:

```text
0a. ^ $ x                  -> ^ x
0b. ^ x $ y                -> ^ x y
1.  ^ ^ x $ y              -> x
2.  ^ (^ x) y $ z          -> (x z) (y z)
3a. ^ (^ w x) y $ ^        -> w
3b. ^ (^ w x) y $ (^ u)    -> x u
3c. ^ (^ w x) y $ (^ u v)  -> y u v
```

Layer 0 has no literals, names, syntax tags, cells, opcodes, machine state,
effects, environments, modules, or evaluation order policy beyond the pure
reduction relation above.

### Rationale

Layer 0 gives v0 its minimal reflective substrate: rule 3 branches on the shape of
a value. Higher layers may add practical representation and execution machinery,
but they must not change these rules for the delta/triage case.

### Open

None for the current v0 spec.

### Notes

- `$` is explanatory notation for this section only.
- Proper lists are a higher-layer convention encoded with right-nested forks:
  `[x, y, z] == ^ x (^ y (^ z ^))`, `[] == ^`.
- Confluence/order-independence is relied on only in the pure Layer 0 setting.
  Once effects or host operations exist, Layer 5 must define observable order.
- Older notes sometimes describe literals or opcodes as leaf/stem/fork-shaped.
  That is a higher-layer compatibility claim, not Layer 0 vocabulary.

## L1 Cells

### Spec

Layer 1 is the storage layer for compact tree-shaped data.

A cell root denotes a stored node graph. Nodes are typed and have storage arity:

```text
arity 0: node with no children
arity 1: node with one child
arity 2: node with two children
```

Leaf/stem/fork are Layer 0 triage shapes. Layer 1 arity is storage structure.
Only `DELTA0/1/2` directly represent those triage shapes.

Layer 1 must be able to store at least these node families:

```text
DELTA0/1/2      triage-compatible leaf/stem/fork nodes
VALUEF0/1/2     fixed-size payload value nodes
VALUEV0/1/2     byte payload value nodes
APPLY           binary application-structure node
REF             storage reference to another node
```

`DELTA0/1/2` are the Layer 1 representation of Layer 0 shapes. `VALUE*` nodes are
payload-bearing data nodes. `APPLY` records application structure as data; it does
not perform application. `REF` is graph-organization machinery: it points from one
stored node to another and permits sharing/compact layout. It is not a
language-level value.

Cells are inert. Storing a node never evaluates it, dispatches it, performs an
effect, or resolves a name. Evaluation belongs to later layers.

Layer 1 includes a portable binary cell ABI for persisted bytecode. Current stable
wire tags are:

```text
0x80  DELTA0       tag
0x81  DELTA1       tag + left ref
0x82  DELTA2       tag + left ref + right ref
0x83  VALUEF0      tag + i64 payload
0x84  VALUEF1      tag + i64 payload + left ref
0x85  VALUEF2      tag + i64 payload + left ref + right ref
0x86  VALUEV0      tag + uleb128 byte length + bytes
0x87  VALUEV1      tag + uleb128 byte length + bytes + left ref
0x88  VALUEV2      tag + uleb128 byte length + bytes + left ref + right ref
0x89  APPLY        tag + left ref + right ref
00xxxxxx xxxxxxxx  REF14 signed relative byte offset
01xxxxxx ...       REF62 signed relative byte offset
```

Fixed integer payloads are stored as little-endian `i64`. Reference payloads are
signed relative byte offsets. `REF14` and `REF62` are wire layouts for the same
semantic `REF` node.

Allocation strategy, free-list policy, in-memory C enum values, and debug printing
are implementation details. Canonical text serialization for cells is required but
not yet specified.


### Rationale

v0 needs a concrete representation that preserves tree shape and remains
inspectable. Separating cells from evaluation prevents old designs from smuggling
machine behavior into storage.

`APPLY` is a separate node because application structure must survive as data.
Encoding application only by adjacency or stack scheduling loses homoiconic
structure needed by later syntax/specialization work.

### Open

- Exact direct node families and wire tags for `LOCAL`, generic `OPCODE`, and
  any other nodes introduced by specialization. They are real node families, not
  payload encodings hidden inside `VALUE*`.
- Canonical text serialization for cells. Current code can format parsed source
  trees canonically and can encode source trees into cells; it does not yet define
  a canonical cell-to-text format.

### Notes

- Current C code exposes `CELLS_NODE_TYPE_ITEMS` in `reducer/cells_api.h` with
  `DELTA*`, `VALUEF*`, `VALUEV*`, `APPLY`, old `OP_FN*`, and `REF`. The matching
  wire ABI lives in `reducer/cells_impl.h` / `reducer/cells_cells.c`.
- Current C code still contains `OP_FN0/1/2`; they are historical implementation
  artifacts for an older function opcode experiment, not part of this spec.
- Historical hint, 2026-02-04: earlier notes tried to make every node uniformly
  leaf/stem/fork-shaped and inspectable via `get_type` / `get_payload`. Current
  spec keeps the useful storage idea but does not decide runtime inspection here.
- Historical hint, 2026-02-09: earlier notes explored compact byte tags and
  variable-width refs. Current spec leaves exact wire encoding open.

## L2 Syntax

### Spec

Layer 2 is the source language and its inert parsed representation.

Source text is UTF-8. v0 is a minimal kernel syntax. Unless this spec says a form
belongs to v0, it belongs to a separate vf (`v*`) language, even if a shared parser can recognize it.

Current v0 syntax includes literals, identifiers, grouping, postfix calls, labeled
arguments, list syntax, and `do ... end` block arguments. Newlines may be
converted to semicolons in layout-active contexts.

Layer 2 syntax is nameful data. It records source structure; it does not evaluate,
resolve names, dispatch opcodes, or introduce runtime bindings.

Core source atoms:

```text
^               triage delta literal
123             signedness/width interpreted by later lowering; current target is i64
{bytes}         byte/string literal
name            identifier
```

v0 source structure forms:

```text
(expr)                      grouping
[x1, x2, ...]               list syntax; desugars during Layer 2 normalization
f(arg1, ..., argN)          call syntax; f() means f(^)
f label: expr               labeled argument application
f do expr1; ...; exprN end  block argument application
```

After parsing, source is normalized into a bootstrap syntax term. Normalization is
where purely syntactic rewrites happen. In particular, list syntax desugars here to
right-nested Layer 0-style lists; it is not delayed to specialization.

Specialization is reserved for work that depends on runtime compilation context:
name binding, recognition of executable constructs, and decisions that cannot be
made by purely local parsing/normalization.

Normalized v0 syntax uses ordinary Layer 1-storable values plus source tags such
as:

```text
:id, :block, :group, :label
```

Examples of normalized syntax shape:

```text
x                   ->  [{:id}, {x}]
[x, y]              ->  ^ [{:id}, {x}] (^ [{:id}, {y}] ^)
(expr)              ->  [{:group}, expr]
f(x, y)             ->  {@} ({@} f x) y
f name: expr        ->  {@} f [{:label}, {name}, expr]
f do a; b end       ->  {@} f [{:block}, a, b]
```

`{@}` is normalized-term application marker. It is not source `@` annotation
syntax: `@[...]` is a Layer 2 parser form, while `{@}` is byte data in a normalized
term. Normalization turns `{@}` into Layer 1 `APPLY` structure.

Tags describe source syntax only. `:block`, `:id`, `:label`, and similar tags have
no machine behavior by themselves.

Application is present in Layer 2 syntax as source structure. It is not Layer 0
application reduction and not Layer 5 runtime dispatch. Later translation may
encode it as Layer 1 `APPLY` nodes.

Spans/locations are diagnostic metadata. They are not part of syntax meaning.

### Rationale

Layer 2 makes v0 writable and transformable without giving source forms runtime
meaning. Nameful inert syntax gives bootstrap code something inspectable; Layer 3
is responsible for deciding which names and source patterns become executable
constructs.

The shared parser may recognize more forms than v0 uses. Those forms are specified in the vf (`v*`) spec, not here.

### Open

- `$` executable-construction protocol semantics remain to be specified.
- Exact diagnostic term shape for parse errors remains open.

### Notes

- Current C implementation parses text into host `source_tree_t`, can format it
  canonically, and `bytecode_source_encode` can encode normalized syntax into
  cells. That pipeline is implementation evidence, not a requirement that runtime
  syntax must be represented by `source_tree_t`.
- Historical hint, 2026-05-28/2026-06-11: newer syntax experiments explored this
  Algol-like/postfix grammar and are preserved in `.memsearch/memory/artifacts/`.
- `$` is a special lexer/parser token admitted where an identifier callee may
  occur. It uses ordinary application and label syntax: `$ f: x do: x + 1` parses
  structurally like `foo f: x do: x + 1`. Every reserved block word followed
  immediately by `:` is a label in every labeled-argument position: `do:` and
  `end:` are labels; bare `do ... end` remains block syntax. Parser implementation
  must add this general disambiguation.
- Historical hint, 2026-07-10: previous restoration used `do!` as provisional
  spelling for syntax rather than runtime opcode. `$` replaces that spelling.

## L3 Specialization

### Spec

Layer 3 is the activation-time specialization relation for syntax terms in
executable positions.

There is no language-level quoting rule and no user-visible `specialize` function
or opcode. A term has no intrinsic executable/data tag. Its role comes from
position: in data position it is an ordinary value; in executable position an
executable-position protocol activates it as syntax to execute.

Input:

```text
term in executable position + executable-position context
```

The executable-position context is supplied by the surrounding v0 protocol. For
example, a `$ fn: [x] do ... end` function body supplies binders for its body.
A term that denotes identifier syntax for `x` resolves through that body context
only when activated as that body. The same term outside executable position remains
ordinary data.

The context contains at least:

- lexical binders supplied by the executable position;
- the fixed native registry of intrinsic executable names;
- diagnostic context for reporting activation/specialization errors.

Output is a closed executable term encoded in Layer 1 cells. Its abstract vocabulary is:

```text
e ::= DELTA | I64(n) | BYTES(bs) | APPLY(e, e) | LOCAL(n) | OPCODE(state)
```

Meanings:

```text
DELTA          executable triage delta value
I64(n)         integer value
BYTES(bs)      byte/string value
APPLY(f, x)    executable application structure
LOCAL(n)       lexical address; 0 is nearest binder
OPCODE(state)  native executable state from the fixed registry
```

Specialization performs context-dependent activation only:

- checks that the activated value is valid normalized executable syntax;
- resolves lexical names to `LOCAL(n)`;
- resolves fixed native names to `OPCODE(state)`;
- recognizes v0 executable construction conventions;
- emits or obtains executable cells;
- rejects unresolved free names and malformed executable syntax.

Purely syntactic rewrites belong to Layer 2 normalization, not Layer 3. Caching
specialized executable cells is an implementation optimization, not a semantic
requirement.

Names die during Layer 3 activation. The executable output contains no source
identifiers and no runtime name lookup. An unbound non-native name is an
activation/specialization error.

Executable output is closed. External values enter by explicit function parameters
and application, not by hidden environment injection. v0 has no `GLOBAL` semantic
node in the current spec.

`LOCAL(n)` and `OPCODE(state)` are Layer 3 executable node families. Their exact
Layer 1 wire tags remain open until the cell ABI is extended.

`$` is always bound when activated in executable position. It selects an
executable-construction protocol and supplies its activation context through
ordinary labeled application. `$` itself is not a runtime opcode. Exact `$`
protocols remain open.

Function values, closure representation, forcing, partial application, and the
runtime meaning of `LOCAL(n)` belong to Layer 5. Layer 3 only produces executable
addresses and opcode states that Layer 5 must interpret.

### Rationale

Layer 3 is the semantic boundary where inert term data becomes executable code by
entering executable position. It preserves porosity: terms loaded, parsed, forged,
or constructed later can execute if some protocol activates them as executable
syntax. It keeps v0 analyzable by removing names before execution and by making all
runtime entry points explicit as `LOCAL` or `OPCODE` nodes.

Keeping syntax rewrites in Layer 2 makes specialization smaller: it does not clean
up surface syntax; it activates already-normalized terms under an
executable-position context.

### Open

- Exact `$` executable-construction protocols.
- Exact executable node families and wire tags for `LOCAL` and `OPCODE`.
- Exact native registry inventory.
- Whether grouping tags are always erased before activation or may survive in
  explicit syntax-data protocols.

### Notes

- Historical hint, 2026-07-10: previous restoration removed runtime `{fn}` syntax
  from v0 and used `do!` as provisional source convention. Current `$` spelling
  keeps its executable-construction protocol open.
- Historical hint: CESK draft used `GLOBAL`; current spec does not include it.
  Cross-unit and host-provided values should be modeled by explicit parameters and
  application unless a later decision reopens global/constant-pool semantics.
- Triage-calculus grounding: expressions use delta and application, irreducible
  expressions are values/programs, and triage rules reflect on value shape.
  Vetochka preserves this no-quote substrate and adds executable-position
  activation as its language/runtime discipline.

## L4 Backbone facilities

### Spec

Layer 4 exposes the minimal host-facing facilities needed for programs to build
code graphs and language/module systems themselves.

Backbone native names:

```text
load_file  :: path-bytes -> bytes | diagnostic
parse_term :: source-bytes -> normalized syntax term | diagnostic
```

`load_file` is the only required host effect in v0. It maps a byte path to file
bytes or a diagnostic. v0 does not define module roots, import names, dependency
resolution, package discovery, caching, authority policy, or path search rules.
Those are module-system policy built above this layer.

`parse_term` is pure. It accepts full shared Vetochka syntax and returns the same
normalized syntax term shape used by Layer 2. It assigns no vf or executable
meaning to that term. The result is ordinary term data until an executable-position
protocol activates it, which invokes Layer 3 specialization.

No `specialize`, `execute`, or `eval` intrinsic exists in v0. Execution is not a
callable operation. It is the semantic event of a term entering executable position:

```text
term data
  -> executable position supplies activation context
  -> Layer 3 activation-time specialization
  -> Layer 5 execution of specialized executable root
```

A module system can therefore be written as ordinary Vetochka code:

```text
path bytes -> load_file -> source bytes -> parse_term -> syntax term
    -> programmer-defined graph/dependency/transformation policy
    -> chosen term enters executable position
```

### Rationale

Reusable code needs two primitive abilities: obtain source bytes and turn source
bytes into inspectable term structure. Everything else about modules is policy.
Keeping only `load_file` and `parse_term` in v0 lets programmers define their own
module systems, import rules, build graphs, and vf languages without extending the
host runtime.

Making execution an intrinsic would turn activation into an ordinary callable,
forcing v0 to specify argument mode, recursive machine entry, authority, and effect
ordering for an `eval`-like operation. Executable position is the cleaner boundary:
it preserves forgedness and porosity without adding a language-level quote/eval
pair.

### Open

- Exact diagnostic term shapes for `load_file` and `parse_term`.
- Exact path byte interpretation and authority boundary for `load_file`.
- Whether parsed normalized terms are always stored in cells or may be represented
  by another explicit term object.

### Notes

- Historical module notes separated module discovery from module semantics. L4
  keeps that split: the host can expose bytes; programmer code decides what those
  bytes mean in a code graph.
- Previous snapshots listed `{specialize}` as a backbone intrinsic. That is
  superseded by activation-time specialization: specialization happens when a term
  enters executable position, not when a user calls an intrinsic.
