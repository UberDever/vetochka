# Vetochka v0 runtime

## Entry

`02_concrete_syntax.md` parses source into cell data. CESK starts at a chosen root
and executes that cell data directly. No intermediate conversion phase exists.

## Host facilities

### Spec

Host facilities expose minimal host-facing operations for code graphs and language/module systems.

Backbone facilities are selected through `$`:

```vetochka
$load_file: path
$parse_term: bytes
```

```text
load_file  :: path-bytes -> {:ok, bytes} | {:error, diagnostic}
parse_term :: source-bytes -> {:ok, cell-data} | {:error, diagnostic}
```

`load_file` is the only required host effect in v0. It maps a byte path to file
bytes or a diagnostic. v0 does not define module roots, import names, dependency
resolution, package discovery, caching, authority policy, or path search rules.
Those are module-system policy built above this layer.

`parse_term` is pure. It accepts full shared Vetochka syntax and returns parsed cell
data. It assigns no vf or runtime meaning to that data.

CESK executes a chosen cell root. Execution is not a callable operation.

A module system can therefore be written as ordinary Vetochka code:

```text
path bytes -> $load_file -> source bytes -> $parse_term -> syntax term
    -> programmer-defined graph/dependency/transformation policy
    -> chosen term enters executable position
```

### Rationale

Reusable code needs two primitive abilities: obtain source bytes and turn source
bytes into inspectable term structure. Everything else about modules is policy.
Keeping only `load_file` and `parse_term` in v0 lets programmers define their own
module systems, import rules, build graphs, and vf languages without extending the
host runtime.

### Open

- Exact diagnostic term shapes for `load_file` and `parse_term`.
- Exact path byte interpretation and authority boundary for `load_file`.
- Exact parsed-cell ownership and lifetime.

### Notes

- Historical module notes separated module discovery from module semantics. L4
  keeps that split: the host can expose bytes; programmer code decides what those
  bytes mean in a code graph.

## Execution machine

### Spec

CESK gives cell terms their operational meaning.

Tree calculus supplies delta/triage rules. CESK owns application order, lexical
environments, runtime dispatch, effects, and traps. It preserves delta rules.

An implementation may use a CEK subset while no store is required. The pure triage
configuration grammar and transitions are specified below; runtime-family
configurations and their remaining transitions remain open. The account uses the
ordinary small-step form:

```text
⟨control, E, kontinuation⟩ -> ⟨control', E', kontinuation'⟩ : effect
```

rather than hiding execution order in a big-step result relation.

### Pure triage transitions

The machine uses effect-labelled CEK configurations:

```text
⟨control, E, kontinuation⟩
-> ⟨control', E', kontinuation'⟩ : effect
```

A terminal machine outcome is `HALT(term)` or `TRAP(diagnostic)`. The current
complete control and kontinuation grammar is:

```text
control ::= RUN(term)
          | SHAPE(term)
          | RETURN(term)
          | SHAPE-RETURN(LEAF | STEM(term) | FORK(term, term))

kontinuation ::= HALT
               | ARG(term, kontinuation)
               | R3(w, x, y, E, kontinuation)
               | RESHAPE(kontinuation)
               | RESTORE(E, kontinuation)

effect ::= τ
         | trap(diagnostic)
         | host(operation, input, output)
```

`τ` is a silent pure transition. `trap(diagnostic)` halts v0 execution. Expected
user failure remains ordinary term data such as `{:error, diagnostic}` and therefore
uses `τ`; it is not a machine trap. `host` records an observable host interaction;
its concrete operations and input/output terms are specified by the runtime-family
rules that perform them.

`E` is the active lexical environment. `RUN` executes a term, `ARG` retains one
unevaluated application operand, and `RETURN` gives a completed triage factor to its
kontinuation. `SHAPE` obtains a triage shape only when Rule 3 requires it. `TERM`
construction preserves an already-inner TERM association.

The following transitions are the current delta, TERM, and ID subset. Other runtime
families add further transitions later.

```text
RUN-DELTA0
  ⟨RUN(DELTA0), E, K⟩
  -> ⟨RETURN(DELTA0), E, K⟩ : τ

RUN-DELTA1
  ⟨RUN(DELTA1(x)), E, K⟩
  -> ⟨RETURN(DELTA1(x)), E, K⟩ : τ

RUN-DELTA2
  ⟨RUN(DELTA2(x, y)), E, K⟩
  -> ⟨RETURN(DELTA2(x, y)), E, K⟩ : τ

RUN-APPLY
  ⟨RUN(APPLY(f, x)), E, K⟩
  -> ⟨RUN(f), E, ARG(TERM(x, E), K)⟩ : τ

RUN-LENS
  ⟨RUN(LENS(l)), E, K⟩
  -> TRAP(non-callable-lens) : trap(non-callable-lens)

ENTER-TERM
  ⟨RUN(TERM(t, Eterm)), Ecaller, K⟩
  -> ⟨RUN(t), Eterm, RESTORE(Ecaller, K)⟩ : τ

RUN-ID
  ⟨RUN(ID(name)), E, K⟩
  -> ⟨RUN(lookup(E, name)), E, K⟩ : τ

APPLY-TERM
  ⟨RETURN(TERM(t, Eterm)), Ecaller, ARG(a, K)⟩
  -> ⟨RUN(t), Eterm, ARG(a, RESTORE(Ecaller, K))⟩ : τ

RESTORE-DELTA0
  ⟨RETURN(DELTA0), Eterm, RESTORE(Ecaller, K)⟩
  -> ⟨RETURN(DELTA0), Ecaller, K⟩ : τ

RESTORE-DELTA1
  ⟨RETURN(DELTA1(x)), Eterm, RESTORE(Ecaller, K)⟩
  -> ⟨RETURN(TERM(DELTA1(x), Eterm)), Ecaller, K⟩ : τ

RESTORE-DELTA2
  ⟨RETURN(DELTA2(x, y)), Eterm, RESTORE(Ecaller, K)⟩
  -> ⟨RETURN(TERM(DELTA2(x, y), Eterm)), Ecaller, K⟩ : τ

TRIAGE-0A
  ⟨RETURN(DELTA0), E, ARG(x, K)⟩
  -> ⟨RETURN(DELTA1(x)), E, K⟩ : τ

TRIAGE-0B
  ⟨RETURN(DELTA1(x)), E, ARG(y, K)⟩
  -> ⟨RETURN(DELTA2(x, y)), E, K⟩ : τ

TRIAGE-1
  ⟨RETURN(DELTA2(DELTA0, x)), E, ARG(y, K)⟩
  -> ⟨RUN(x), E, K⟩ : τ

TRIAGE-2
  ⟨RETURN(DELTA2(DELTA1(x), y)), E, ARG(z, K)⟩
  -> ⟨RUN(APPLY(APPLY(x, z), APPLY(y, z))), E, K⟩ : τ

R3-ENTER
  ⟨RETURN(DELTA2(DELTA2(w, x), y)), E, ARG(z, K)⟩
  -> ⟨SHAPE(z), E, R3(w, x, y, E, K)⟩ : τ

SHAPE-DELTA0
  ⟨SHAPE(DELTA0), E, K⟩
  -> ⟨SHAPE-RETURN(LEAF), E, K⟩ : τ

SHAPE-DELTA1
  ⟨SHAPE(DELTA1(u)), E, K⟩
  -> ⟨SHAPE-RETURN(STEM(TERM(u, E))), E, K⟩ : τ

SHAPE-DELTA2
  ⟨SHAPE(DELTA2(u, v)), E, K⟩
  -> ⟨SHAPE-RETURN(FORK(TERM(u, E), TERM(v, E))), E, K⟩ : τ

SHAPE-APPLY
  ⟨SHAPE(APPLY(f, x)), E, K⟩
  -> ⟨RUN(APPLY(f, x)), E, RESHAPE(K)⟩ : τ

SHAPE-MATERIALIZE-LENS
  if lens-initial(t, E) = l:
  ⟨SHAPE(t), E, K⟩
  -> ⟨SHAPE(LENS(l)), E, K⟩ : τ

SHAPE-NO-LENS
  if lens-initial(t, E) is undefined:
  ⟨SHAPE(t), E, K⟩
  -> TRAP(no-triage-lens) : trap(no-triage-lens)

SHAPE-LENS-LEAF
  if lens-view(l) = LEAF:
  ⟨SHAPE(LENS(l)), E, K⟩
  -> ⟨SHAPE-RETURN(LEAF), E, K⟩ : τ

SHAPE-LENS-STEM
  if lens-view(l) = STEM(lu):
  ⟨SHAPE(LENS(l)), E, K⟩
  -> ⟨SHAPE-RETURN(STEM(LENS(lu))), E, K⟩ : τ

SHAPE-LENS-FORK
  if lens-view(l) = FORK(lu, lv):
  ⟨SHAPE(LENS(l)), E, K⟩
  -> ⟨SHAPE-RETURN(FORK(LENS(lu), LENS(lv))), E, K⟩ : τ

RESHAPE-RETURN
  ⟨RETURN(v), E, RESHAPE(K)⟩
  -> ⟨SHAPE(v), E, K⟩ : τ

R3-LEAF
  ⟨SHAPE-RETURN(LEAF), Earg, R3(w, x, y, Ecallee, K)⟩
  -> ⟨RUN(w), Ecallee, K⟩ : τ

R3-STEM
  ⟨SHAPE-RETURN(STEM(u)), Earg, R3(w, x, y, Ecallee, K)⟩
  -> ⟨RUN(APPLY(x, u)), Ecallee, K⟩ : τ

R3-FORK
  ⟨SHAPE-RETURN(FORK(u, v)), Earg, R3(w, x, y, Ecallee, K)⟩
  -> ⟨RUN(APPLY(APPLY(y, u), v)), Ecallee, K⟩ : τ

HALT-RETURN
  ⟨RETURN(v), E, HALT⟩
  -> HALT(v) : τ
```

The direct `SHAPE-*` delta rules, `SHAPE-APPLY`, and `SHAPE-LENS-*` are disjoint.
`SHAPE-MATERIALIZE-LENS` / `SHAPE-NO-LENS` apply only to a term that is not delta,
APPLY, or already a LENS. Thus a non-delta runtime family, including TERM, is
inspected only through its LENS contract; LENS does not recursively materialize a
second lens.

`lens-initial(t,E)` either constructs private LENS state for the runtime family of
`t` or is undefined. `lens-view(l)` returns `LEAF`, `STEM(lu)`, or `FORK(lu,lv)`;
its derived states preserve the inspection provenance of selected children. These
are implementation-defined ABI operations whose family-specific definitions remain
open.

`SHAPE-APPLY` is the intentional replacement for the current reducer's incorrect
storage-arity classification of `APPLY`: it executes the application through normal
callee-first control, then resumes the pending Rule 3 shape request. TERM entry
installs its environment in machine state; `RESTORE-*` materializes one root TERM
when a structural result leaves that active environment. No general representation
equivalence is assumed.

### Executable application

Executable application is callee-first. Semantically:

```text
TERM(APPLY(f, x), E)
```

first executes `TERM(f, E)` and retains `TERM(x, E)` as one pending argument. The
callee's runtime family/state decides whether to retain, inspect, or eagerly execute
that pending argument.

Delta stores its pending argument without forcing it. In particular, a stored
argument retains its caller TERM environment. Rule 1 discards its argument. Rule 2
preserves the callee environment on its selected branches and duplicates the caller
TERM environment on both uses of its argument.

Rule 3a/3b/3c are structural rewrites, not application-reduction rules. But when
Layer 5 needs the triage shape of a Rule 3 argument whose top-level node is `APPLY`,
it schedules that application and retains a continuation which resumes Rule 3 on the
result. An arbitrary application is never classified as fork merely from storage
arity.

### TERM and lexical identifiers

`TERM(root; private E)` is a runtime family carrying objective lexical context.
`E` is opaque and unforgeable.

```text
TERM(TERM(root, Einner), Eouter) = TERM(root, Einner)
```

A child selected from a TERM structural view retains the same `E`; a child already
carrying a TERM retains its inner environment. An implementation may thread `E`
without allocation while descending, but must preserve TERM association when a term
returns, is stored, becomes pending, or crosses a continuation/frame.

`ID(name)` is a separate runtime node family. Under executable-usage traversal:

```text
TERM(ID(name), E) -> lookup(E, name)
```

Identifier syntax/data is not thereby always resolved: construction or declaration
traversal may preserve it as syntax. An absent binding is a hard trap when executable
usage demands it. `LOCAL` is not a v0 semantic node or ABI; a private resolved-slot
cache is permitted only as an observationally equivalent optimization.

Closure application extends the closure's defining `E` with its parameter bindings;
the caller environment does not merge into that captured environment.

### Triage observation

Rule 3 asks for the current triage view of its argument. The Rule 3 rewrite does
not itself execute an `APPLY` chain; L5 shape demand schedules a top-level `APPLY`
and resumes Rule 3 on its result rather than classifying `APPLY` from storage arity.

Pure delta view recognizes the application-first delta forms:

```text
DELTA0                         leaf
APPLY(DELTA0, u)               stem(u)
APPLY(APPLY(DELTA0, u), v)     fork(u, v)
```

Thus `APPLY(APPLY(DELTA0, u), v)` reaches the calculus form `^ u v` by explicit
Rules 0a/0b; it is not a separate source fork constructor. An arbitrary application
spine is not a fork merely because it has two cell children.

`REF` is transparently dereferenced before triage and has no independent triage
meaning.

Every non-delta runtime family requires a specified triage traversal/projection.
That traversal is internal machine semantics, not a user-visible reflection API.
Rule 3 remains the language-level structural observation mechanism.

### Runtime cell node type registry

Each opcode transition state is a concrete cell node type in one global opcode-state
table. Actual cell encoding codes are allocated only after that table stabilizes.
`OPCODE_EXT1`–`OPCODE_EXT4` reserve four separate extension namespaces/states for
future arbitrary states. This registry describes storage and points to CEK/lens
behavior; it does not restate transitions, effects, or traps.

Fixed integer payloads use little-endian `i64`. References use signed relative byte
offsets. `REF14` and `REF62` are two wire layouts for semantic `REF`.

| Wire | Cell node type | State / use | Cell representation | Inspection | CEK references |
|---|---|---|---|---|---|
| `0x80` | `CELLS_NODE_TYPE_DELTA0` | delta leaf | tag | direct leaf | `RUN-DELTA0`, `TRIAGE-0A`, `SHAPE-DELTA0` |
| `0x81` | `CELLS_NODE_TYPE_DELTA1` | delta stem | one child reference | direct stem | `RUN-DELTA1`, `TRIAGE-0B`, `SHAPE-DELTA1` |
| `0x82` | `CELLS_NODE_TYPE_DELTA2` | delta fork | two child references | direct fork | `RUN-DELTA2`, `TRIAGE-1/2`, `R3-*`, `SHAPE-DELTA2` |
| `0x83` | `CELLS_NODE_TYPE_VALUEF0` | fixed integer leaf | `i64` | `LENS_VALUEF0` — pending | pending |
| `0x84` | `CELLS_NODE_TYPE_VALUEF1` | fixed integer stem | `i64` + child | `LENS_VALUEF1` — pending | pending |
| `0x85` | `CELLS_NODE_TYPE_VALUEF2` | fixed integer fork | `i64` + children | `LENS_VALUEF2` — pending | pending |

`OP_FN0/1/2` are legacy current implementation types and are not target registry
states. No separate closure type is allocated yet: decide first whether closure is a
runtime state among opcode states.

### Opcodes and `$`

Each opcode transition state is a concrete cell node type with state-specific
private state. Its LENS contract supplies the stable calculus-facing projection.
Argument transport and each state’s input protocol are specified by CEK rules.

Each received opcode input is represented as one ordinary argument record:

```text
[{:pos},   ^,   payload]
[{:label}, key, payload]
```

Layer 2 labels remain encoded term data; CESK has no separate label-metadata state.
At opcode entry a non-label postfix operand, including a block term, becomes a
`:pos` record.

An opcode state receives operands one at a time and returns one of:

```text
Continue(next-state, inputs)
Dispatch(result)
hard trap
```

Its per-state policy decides whether payload is retained as syntax, demanded eagerly
in caller context, or routed by label. Exact state transitions and triage traversal
of opcode children remain open.

The currently selected `$` protocol subset is:

```vetochka
$f: x do: body
$f: x do: body to: argument
$fn: [x, y, ...] do body-forms end
$fn: [x, y, ...] do body-forms end to: argument
```

`$f` constructs an eager one-argument closure. `$fn` constructs an eager
multi-argument closure with block body. `$form` is not a v0 protocol. A closure
accepts only labeled `to:` as its call operand; another label or positional operand
hard-traps. Parenthesized postfix calls have no v0 function-call semantics, though
shared vf syntax may retain them.

`$load_file` and `$parse_term` are selected `$` protocols. Their routed payloads are
eager; expected failure is ordinary `{:ok}`/`{:error}` term data, while protocol and
runtime failures hard-trap.
