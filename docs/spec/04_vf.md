# Vetochka vf (`v*`) languages

Status: draft spec, recomposed 2026-07-11. OBSOLETE where it contradicts
`docs/new_spec/` and `.memsearch/memory/2026-08-30.md` (notably: mixed infix
chains are allowed).

## Naming

**vf** is the Vetochka language family built above v0.

`v*` denotes this family.

## Syntax layer

v0 is a vf subset. Any v0 code may occur unchanged as ordinary vf code.

A vf language adds source forms and programmer-written interpretation above that
v0 subset. Vetochka provides v0 protocols for introspection, runtime term forging,
and compilation; programmers use those protocols to build the vf language they
want.

Current vf source forms outside v0:

```text
@[a, b, ...] expr            annotation with comma-list payload
f[arg1, ..., argN]           bracket/list-payload application
f{bytes}                     byte-payload application
prefix-op expr               prefix syntax
x op y op z                  flat infix syntax for one repeated operator
base.name                    selector syntax
```

Annotations use a comma-list payload. Rationale: comma-list annotations are easier
to parse, easier to process later, and read better than encoding multiple items in
one expression.

Infix has no precedence. One infix chain may contain only one byte-identical
operator token. Normalization keeps infix flat and does not choose associativity.

`$` is v0's special executable-construction token, not a runtime opcode. Because
v0 is a vf subset, vf code may contain `$` unchanged as ordinary v0 code and use
its ordinary labeled application structure. `$` protocol semantics remain specified
by v0, not by a vf parser extension.

## Normalized syntax

A vf language may preserve extended source forms as tagged normalized terms:

```text
@[a, b] expr          ->  [{:annot}, ^ a (^ b ^), expr]
f[arg1, ..., argN]    ->  {@} f (^ arg1 (... (^ argN ^)))
f{bytes}              ->  {@} f {bytes}
prefix-op expr        ->  [{:prefix}, {op}, expr]
x op y op z           ->  [{:infix}, {op}, x, y, z]
base.name             ->  [{:selector}, base, {name}]
```

Ordinary list syntax desugars to ordinary proper lists; it is not preserved as
`:list` metadata.

Existing syntax is the vf data/DSL substrate. Application, labels, lists,
annotations, prefix/infix shape, selectors, and byte payloads can express friendly
user-defined structures without new literal grammar:

```vetochka
set[red, green, blue]

map[
    entry key: {host} value: {localhost},
    entry key: {port} value: 8080,
]
```

Here parser supplies only structure. Programmer-written vf code assigns meanings to
`set`, `map`, `entry`, keys, duplicate handling, ordering, and representation.

Do not add literal grammar merely to make a data structure prettier. Add syntax
only after demonstrating that existing structure cannot preserve a required
semantic distinction.

## Historical grammar note

The old `docs/grammar.md` mixed v0, vf syntax, cell encoding, and runtime
opcode protocol. It has been moved to
`.memsearch/memory/artifacts/grammar.md` as a historical design artifact.

Useful parts retained here:

- UTF-8 source text;
- `do` and `end` as block delimiters;
- annotations, selectors, prefix/infix, bracket calls, and byte calls as extended
  syntax forms;
- no precedence and no mixed infix chains.

Rejected from that old grammar as current spec:

- v0 as only application/delta/i64/string;
- `{fn}` as source/runtime meaning;
- cell encoding inside grammar;
- opcode dispatch inside grammar.

## Notes

`vmeta` and `vsystem` are possible far-future names for different uses of vf:
metaprogramming/module/source transformation versus C-facing systems work. They are
speculative and not addressed by this spec.
