# Transparent tagging candidate

- Question (user): how to implement tagged values and Barry Jay's hidden tagging.
- Status (agent): a candidate derived from the current triage rules. No integration decision or production implementation.
- Criteria (agent): preserve application behavior, recover annotations structurally, and permit construction from the same observable tree.

## Source and distinction

- Evidence (agent): Jay defines `tag`, `getTag`, and `untag`, with laws for application forwarding and both projections.
- Source: https://raw.githubusercontent.com/barry-jay-personal/tree-calculus/master/Intensional_Programs.v

- Source: https://raw.githubusercontent.com/barry-jay-personal/tree-calculus/master/Tree_Calculus.v
- Finding (agent): “hidden” means absent from the forwarded application result. The annotation remains observable through structure.
- Boundary (agent): `[kind, meta, ...payload]` is a record convention. A transparent wrapper is a particular executable tree.
- Finding (agent): a record head alone does not make ordinary triage application delegate to its payload. Native record execution requires the machine's recognition contract.

## Construction under Vetochka's rules

The following are construction abbreviations, not new primitives or proposed surface syntax.
Expand each abbreviation to a tree before inspection.

```text
K = ~[~[]]
I = ~[~[K], K]
S(a, b) = ~[~[a], b]
case(a, b, c) = ~[~[a, b], c]

tag(t, f) = S(S(K(K), f), K(t))
```

`K(v)` constructs `~[~[], v]`. Thus the complete wrapper has a stem on the left and a constant holding `t` on the right.

- Derivation (agent): rule 2 and the constant rule give the following reduction. The final constant discards its argument without evaluating it.

```text
tag(t, f)(x)
  -> (S(K(K), f)(x))(K(t)(x))
  -> ((K(K)(x))(f(x)))(K(t)(x))
  -> (K(f(x)))(K(t)(x))
  -> (~[~[], f(x)])(K(t)(x))
  -> f(x)
```

- Finding (agent): this is five head-reduction steps, including the constructor step for `K(f(x))`.
- Design choice (agent): the right branch is `K(t)`, so it does not apply the annotation as a function.
- Scope (agent): this establishes a reduction path in the pure core. It does not prove full-machine contextual equivalence or an effect-order theorem.

## Structural readers

The tag is the right child of the wrapper's right child.
The wrapped value is the right child of the fork inside the wrapper's left stem.

```text
right = case(~[], ~[], K(I))
getTag = case(~[], ~[], K(right))
readInner = case(~[], right, ~[])
untag = case(~[], ~[], S(K(K), readInner))
```

- Finding (agent): these readers dispatch directly on children. They do not require Rule 3 to evaluate a pending projection.
- Candidate laws (agent): `getTag(tag(t, f))` reduces to `t`, and `untag(tag(t, f))` reduces to `f`.
- Boundary (agent): the laws concern inputs constructed by `tag`. The fallback branches do not define a validated or authenticated tagging protocol.
- Open (agent): whether user-facing readers should reject malformed wrappers or retain these structural projection conventions.

## Integration alternatives

- Option (agent): retain designator-headed records for native values and use the transparent tree as a library annotation wrapper.
- Option (agent): give an explicit annotation record a machine delegation rule. This adds semantics and differs observably from the pure wrapper.
- Optimization (agent): store a recognized pure wrapper as annotation and wrapped-value references, then reconstruct its exact tree through piths.
- Constraint (agent): exposing a convenient list instead of that tree changes structural observation. It is not merely storage compression.
- Preference (agent): establish the pure wrapper contract first. Optimize storage only after its application and observation behavior is fixed.
- Version boundary (agent): a version stored as an annotation can describe a contract. If it selects execution behavior, that selection must be explicit.
- Open (agent): choosing the version before constructing `f` could preserve the wrapper law. Interpreting the annotation during application would change that law's scope.
- Open (agent): annotation forwarding does not automatically preserve annotations on returned values or partial applications.

## Tagged integer and tagged pairs

- Representation direction (user): each k-v entry can itself be a hidden-tagged list of length two.
- Assumption for this example (agent): a k-v pair has the bare descriptor `{:kv}`. The user did not choose its exact descriptor schema.
- Assessment (agent): retain the small executable model as a task scratchpad. It gives reproducible reduction evidence without requiring another runtime or parser.

Construction shorthand:

```text

descriptor = [kv({tag}, {:i64}), kv({meta}, [])]
```

- Finding (agent): these names abbreviate expanded trees. The actual integer term needs only nyads and byte strings. Proper lists are nyad chains.
- Finding (agent): labels such as `tag:` are presentation sugar for the tagged pairs in this example. The reducer returns their actual trees.
- Finding (agent): an annotation can itself contain tagged values. This construction does not require a separate native type tag for the integer.
- Qualification (agent): the example retains bare strings and lists as its base structures. It does not mandate recursively tagging every descriptor.
- Scope (agent): `{1234}` is a byte string in the current core syntax. The wrapper provides the requested integer representation, not arithmetic semantics.
- Relation to prior alternatives (agent): the user's direction explores one wrapper for values and metadata entries. It revisits the separate head-record convention.

## Common Lisp property-list comparison

- Question (user): whether hidden tags can provide a facility similar to Common Lisp property lists.
- Assessment (agent): yes, as an extensible collection of named properties attached to a value. The storage format and attachment semantics differ.
- Evidence (agent): a Common Lisp plist alternates keys and values in one even-length list. The first matching entry determines a property's value.
- Source: https://www.lispworks.com/documentation/HyperSpec/Body/26_glo_p.htm#property_list
- Evidence (agent): an association list instead contains cons pairs, with each pair's car as key and cdr as value.
- Interpretation (agent): Vetochka's list of tagged two-element lists is structurally closer to an alist, though it is not the same pair encoding.
- Source: https://www.lispworks.com/documentation/HyperSpec/Body/14_aba.htm
- Evidence (agent): Common Lisp symbols have a dedicated property-list attribute, separate from their value and function attributes.
- Qualification (agent): standard Common Lisp does not attach that symbol property-list slot to every arbitrary value.
- Evidence (agent): symbol-property updates are destructive. Updating a symbol's properties does not annotate the separate value held by that symbol.
- Source: https://www.lispworks.com/documentation/HyperSpec/Body/t_symbol.htm
- Evidence (agent): `get` uses identity-based indicator comparison, `eq`. It accesses the symbol's plist through the same lookup described by `getf`.
- Source: https://www.lispworks.com/documentation/HyperSpec/Body/f_get.htm
- Evidence (agent): `getf` returns a supplied default for an absent key. That result alone cannot distinguish absence from a stored equal default.
- Source: https://www.lispworks.com/documentation/HyperSpec/Body/f_getf.htm
- Proposal (agent): treat the annotation as a property collection. A library lookup could operate on `getTag(value)` without requiring another tag primitive.
- Proposal (agent): immutable property updates can construct a new wrapper around the same payload. Shared mutation would require an additional contract.
- Open (agent): key equality, duplicate keys, absence versus an empty value, and update behavior remain unspecified.
- Constraint (agent): if interning remains a hidden optimization, it must not make equal byte-string keys behave differently based on allocation.
- Boundary (agent): properties are ordinary data. Consumers can interpret them, but attachment alone does not enforce types or select runtime behavior.
- Limit (agent): this comparison uses the HyperSpec. No Common Lisp execution or new lookup implementation was performed.
